# オンライン下書き・公開

`editor.html` の管理者ログインから、Supabase Authで作成した管理者のメールアドレス・パスワードでログインします。パスワードをコードやチャットに記載しないでください。

## 操作
1. 編集するスポットを選びます。
2. カード情報を編集し「選択中の下書きを保存」を押します。
3. 再読み込みして再ログインし、同じスポットの「選択中の下書きを読み込む」を押します。
4. 確認ダイアログで了承すると保存済みの項目を置き換えます。古い下書きでオンライン未保存（NULL）の写真・URLは現在の入力を保持します。空欄として保存したURLは読み込み時にも空欄になります。

## 保存範囲と制限
- オンライン保存は選択中の1スポットの名前・説明文・写真URL・ショート動画URL・Vlog URL・公式サイトURLです。全スポット一括保存ではありません。
- 写真は別枠で非公開アップロードし、公開候補の指定・確認後に公開できます。動画ファイル、GeoJSON、新規スポット追加のオンライン保存は未対応です。
- 公開マップは従来のJSONを土台に、公開済み6項目だけを固定IDで上書きします。オンライン下書きは保存しただけでは公開されません。
- 既存の端末内保存、JSON書き出し、プレビューは独立しています。必要に応じて端末内保存も行ってください。
- ログイン状態はメモリ内だけに保存し、再読み込み後は再ログインが必要です。
- 下書きの同時編集は最後の保存が優先されます。公開時は確認した下書き・公開状態が変わっていると中止します。
- CDNやSupabaseに接続できない場合でも端末内編集は使用できます。

## セキュリティ
`js/publication-data.js` にあるURL・publishable keyは公開用です。secret/service_role keyは置かないでください。
管理者IDの画面上のチェックだけでは保護できません。DBの権限とRLSでアクセスを制限します。
先に `spot_content_drafts` のセットアップSQL、`02-draft-media-fields.sql`、`03-spot-publication.sql` を実行する必要があります。
URLは保存前・読み込み前とも既存のカード入力ルールで検証します。不正な値があれば、カード情報全体の保存・読み込みを中止し現在の入力を保持します。
一般ユーザー登録と匿名ログインはSupabase側で無効にしてください。
認証済み管理者による保存・読み込みは、管理者本人の実アカウントで動作確認してください。

## 公開
1. 再編集するときは、先に「選択中の下書きを読み込む」で既存の下書きを取得します。初期表示は元のJSONです。
2. 6項目を編集し「選択中の下書きを保存」を押します。
3. 「公開内容を確認」を押し、現在の公開内容と保存済み下書きの比較・カード表示を確認します。
4. 「この内容を公開する」を押します。画面の未保存の入力は公開されません。
5. 「利用者マップを確認」で開いた地図を再読み込みし、カード・リスト・ルート内の名称を確認します。

実行後に通信が途切れた場合、公開が完了していても成功表示を受け取れないことがあります。もう一度「公開内容を確認」で現在の内容を取得してから判断してください。

## 直前の公開を取り消す
「直前の公開を取り消す」で戻る内容を確認し、「この内容に戻す」を押します。
初回公開の取り消しは元のJSONに戻ります。取り消せるのは直前の1回で、取り消しの取り消し・複数世代の履歴はありません。下書きと画面の入力はそのまま残ります。

## マップ側の動作と公開サイトへの導入
- 位置、カテゴリ、固定ID、ルートの順番はオンラインのカード更新で変わりません。
- 通常の地図は公開テーブルのみを取得し、下書きや取り消し用データは取得しません。
- Supabase通信が失敗（最大5秒待機）した場合や、公開レコードが不正な場合は元のJSONで表示します。その場合、最新の公開内容とは異なることがあります。
- 下書きプレビューは公開データを取得せず、プレビュー対象の入力をそのまま表示します。
- この連携コードは初回にGitHub Pages側へ反映する必要があります。その後は6項目の変更ごとにGitHubへプッシュする必要はありません。
- ローカルの管理画面も同じSupabaseにつながります。「公開」はテスト専用の保存ではなく実際の公開テーブル更新です。
- 既存のGitHub Pagesがまだ旧コードなら、公開テーブルを更新してもそのページには反映されません。

## 非公開写真のアップロードと公開
前提: `04-private-photos.sql` を実行し、`gyoda-private-photos` が非公開で8件のRLSポリシーが作成されていること。

1. 管理者ログイン後、対象スポットを選びます。
2. 入力欄の下にある「非公開の写真」でJPEG・PNG・WebPを選びます。選ぶだけでは送信しません。
3. 送信前のプレビューを確認して「非公開で保存」を押します。
4. 保存後は「保存済み写真を取得」を押し、一覧から選ぶと認証付きで写真を取得・表示します。再読み込み・再ログイン後も同じ手順で確認できます。

- 原本を直接送らず、ブラウザ内で長辺最大1600pxに縮小・再エンコードします。入力は20MiB・4000万画素以内、出力は最大5MiBです。HEICには対応していません。
- 元の写真ファイル名・EXIF情報をそのまま保存せず、ランダムUUIDをファイル名に使います。ただし写真に写り込んだ個人情報を自動で消す機能ではありません。
- プレビューには認証付きdownloadとBlob URLを使用します。公開URL・署名付き共有URLは作成しません。
- 画像やBlob URLはカードのJSON・localStorageへ保存しません。ログアウト・スポット切替・プレビュー終了時に画像とBlob URLを破棄します。
- 保存済み写真の「この写真を公開候補にする」でオンライン下書きに指定します。この時点ではまだ非公開です。
- 「公開内容を確認」で候補写真と保存済みの文章を確認してから公開すると、サーバーが公開用コピーを作成します。「下書きの写真URLを使う」で従来のURL方式に戻せます。
- 差し替えは別ファイルとして保存します。使用状況一覧から、条件を満たす未使用の非公開写真を確認して削除できます。公開失敗のコピーは失敗確定から24時間以上待って整理できます。詳細は[削除手順](private-photo-deletion.md)・[コピー整理](failed-photo-cleanup.md)を参照してください。
- アップロード中にスポットを切り替えた場合、送信済みの処理は中断できず元スポットに保存されることがあります。元スポットの一覧を取得して確認してください。
- 通信失敗では成功応答だけ届かなかった可能性があるため、一覧を確認してください。再試行は同じ保存先を使用し、上書きや自動の重複保存は行いません。

### 初回の実環境確認
ローカルテストはStorageの応答を模したブラウザテストとRLSのテストです。本番Storageでの管理者認証・ファイル配信の確認は別途必要です。
まず公開して問題のないテスト写真を1枚使い、保存・再ログイン後の表示を確認してください。続いて同じファイルが未ログイン、別ユーザー、publicエンドポイントから取得できないことを確認してから機密写真を扱います。Public設定へ切り替えたり、確認のために署名付きURLを発行したりしないでください。
